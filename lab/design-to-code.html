Design to code

We no longer present static designs. Everything goes straight to code, and that’s what we use as our source of truth. This is part one of a running series. The pilot is still going.

The old way

A web project makes the same work over and over: a whiteboard, wireframes, a presentation file, a design file, a components page, a handoff. Each copy drifts a little from the last. Each discipline names the same thing differently. It’s insane.

[Jamie: one line on what that felt like day to day]

Impossible to cool

The presentation tool we’d used for years shut down. We were really distraught. Nothing anyone tried after that was liked, and nobody liked presenting from the design tool. An earlier attempt to build our own hadn’t worked.

Then one evening, my agent and I built a working review layer: comments pinned to elements on a live page, threads, resolving, export. A prototype, no server. But what was just impossible became cool, and impossible to cool beats cool to cooler.

How it works now

We start with a design system I built with my agent, matched to the framework our developers already use. That became the starter file for our design tools. Instead of presenting static mockups, we build our designs into real code, with Storybook for the components, and that’s the source of truth for requirements.

I designed the dashboard we present work from, with commenting built in. It’s in development now. The demo convinced people more than the slides did. As soon as we got to the demo, it was question, question, question.

What I’m still finding out

Whether the setup pays back on every project or only some. The pilot measures that. Next, content and strategy move into the same artifact.
